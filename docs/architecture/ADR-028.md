## Context

Flutter has zero code today — no `pubspec.yaml`, no `lib/`. Everything else
in ZUKA (48 migrations, 19 completed backend sessions) has momentum; the
frontend has none. Before the first screen gets built, three choices are
genuinely expensive to reverse once dozens of screens depend on them: how
state flows through the app, how navigation/deep-linking works, and how the
codebase is organised. Getting these wrong doesn't show up until screen 15,
by which point changing them is a rewrite. Per the audit's own discipline
(the ADR-027 3-question checklist), none of these should be over-decided
either — pick the minimum viable shape, not a framework.

## Decision

### 1 · State management: Riverpod (`flutter_riverpod` + `riverpod_generator`)

**Reasoning, not just a pick:**
- ZUKA's backend surface is RPC-shaped, not REST-resource-shaped — every
  meaningful action is `supabase.rpc('function_name', params)` returning
  rows or a table, and most reads are already-composed, discovery-feed-style
  queries (`discovery_feed_nearby`) rather than generic CRUD. Riverpod's
  `AsyncNotifier`/`FutureProvider` model maps directly onto "call an RPC, get
  a future, render loading/data/error" — which is *every* screen in
  `ZUKA_DESIGN_LIVING_DOC.md` §1's STATES section (Default/Loading/Empty/
  Offline/Low-data).
- Offline-first (Africa-first, CLAUDE.md §5) needs a clean place to layer
  "check cache, then network, then reconcile" — a Riverpod repository
  provider does this without inventing a separate framework.
- Compile-time-safe DI and strong testability matter for a codebase that
  will be built session-by-session, often by an AI agent picking the work
  back up cold each time — Riverpod's explicit provider graph is easier for
  a fresh session to read correctly than implicit context-based state.
- Lower boilerplate than Bloc for a solo-founder MVP scope; Riverpod is also
  the actively-recommended path from the same author's earlier Provider
  package, so it isn't a niche or high-risk pick.

**Alternative seriously considered — Bloc/Cubit.** Philosophically the
closer fit to ZUKA's own backend culture (explicit event→state transitions
echo the append-only `domain_events` model, ADR-015) and enforces very
strict, auditable state transitions — arguably attractive given how much
this project already values explicit state machines (`ticket.status`,
`gathering.status`). Rejected only on cost: materially more boilerplate per
feature for a solo maintainer, and offline/cache layering is more ceremony
in Bloc than in a Riverpod repository provider. **If the founder weighs
"explicit auditable transitions" higher than "less boilerplate," Bloc is the
correct override — flag it before Session 1, not after 10 screens.**

**Rejected outright:** GetX (community-documented anti-patterns around
implicit global state and poor testability — sits badly against a project
that hard-fails every backend test on purpose); plain `setState`/
`ChangeNotifier` (fine for a prototype, not for an app with real offline
state and 6+ MVP screens already scoped).

### 2 · Navigation: `go_router`

Official Flutter-team package, not a third-party bet — lower long-term risk.
Declarative, URL-based routing with first-class deep-link support, which is
not optional here: `ZUKA_DESIGN_LIVING_DOC.md` §1 already specifies a
shared-card deep-link entry point, and `CONCEPT_Gift_Ticket_Growth_Loop.md`
§5 and `CONCEPT_Poster_Acquisition_Engine.md` §6 both depend on a
`transfer_token`/attribution deep link surviving an app-install round-trip.
`go_router` handles this natively; hand-rolling `Navigator` 1.0/2.0 routing
to get the same guarantee is strictly more work for a worse result.

### 3 · Project structure: light, feature-first — no premature layering

```text
lib/
  app/            bootstrap, DI root, routing table (go_router config),
                  connectivity check, Supabase client init, Sentry init
  core/           the RPC client wrapper (see ZUKA_FLUTTER_RPC_CONTRACT.md),
                  design tokens (see ZUKA_FLUTTER_DESIGN_TOKENS.md),
                  the Shared Component Library widgets (FeedItem, StatusPill,
                  ActionRow, LensControl — per the living doc, not invented)
  features/
    discovery/    screen.dart, widgets/, providers.dart, models.dart
    ticketing/    (same shape)
    scanner/      (same shape)
    vendor/       (same shape)
    ...one folder per real backend domain, not per generic layer
```

**Explicitly not doing:** a `data/domain/presentation` clean-architecture
split with repository/use-case abstraction layers inside each feature. Per
ADR-027's Rule-of-Three: that indirection earns its cost once 3 real features
need to swap their data source or share business logic across layers — at
session 1, with one screen and one RPC, it's pure premature abstraction.
Add the layering to a feature **when a second real need for it appears**,
not before. `core/` holds only what's genuinely shared from day one (the RPC
wrapper, tokens, component library) — everything else stays inside its
feature folder until proven otherwise.

### 4 · Environment config

Supabase URL + anon key via `--dart-define` (or `--dart-define-from-file`
for local dev convenience) — never hardcoded, never committed. Three
environments from day one (dev/staging/prod) even though only dev exists
today (no production Supabase project is linked yet) — cheap to set up now,
expensive to retrofit once build scripts assume one environment.

## Alternatives considered

Covered inline per decision above (Bloc for state management; hand-rolled
`Navigator` for routing; clean-architecture layering for structure). All
rejected on the same principle: pick the shape that's cheapest to extend
later, not the one with the most ceremony now.

## Consequences

**Enables:** a Flutter session can start immediately without re-litigating
these three decisions; every future session reads this ADR instead of
re-proposing an architecture.

**Requires (build work, not started here):** `flutter create`, the `lib/`
skeleton above, `flutter_riverpod` + `riverpod_generator` + `go_router` as
the only new dependencies (ADR-016: propose, don't silently add — this ADR
is that proposal), wiring the RPC client wrapper per
`ZUKA_FLUTTER_RPC_CONTRACT.md`, and the design tokens per
`ZUKA_FLUTTER_DESIGN_TOKENS.md`.

**Constrains:** no feature folder may introduce a `data/domain/presentation`
split, a second state-management library, or a hand-rolled router without a
new ADR or an explicit founder override — these three choices are meant to
hold for the life of the MVP.

**Does not affect:** the backend, the design spec, or any ADR already
governing RPC contracts (ADR-021/022/023) — this ADR is purely about how the
Flutter *client* is organised, not what it calls.
