# ADR-022 — SECURITY DEFINER Helper to Break Circular RLS Recursion

> **Status:** ACCEPTED (in production use since S011)
> **Date:** 2026-07-02
> **Authority:** Architecture Council · Adaptive Zone
> **Relates to:** ADR-016 (Supabase-first, modular monolith, RPC pattern),
> the RLS/grant conventions established S004-S005 (`REVOKE ALL` then
> narrow `GRANT` + `RLS` policy), Vol 04 Ch2 (Tier-1 entity pattern)
> **Discovered:** S011 (vendor-marketplace-foundation), flagged by
> `zuka-reviewer` as a new architectural primitive worth a paper trail

---

## Context

S011 introduced three mutually-referencing Tier-1 tables: `vendor_company`,
`vendor_team`, `vendor_team_member`. The natural RLS shape — "a company's
owner or any of its team members may read the row" — requires each table's
policy to look up rows in the other two:

```
vendor_company's policy   → subqueries vendor_team + vendor_team_member
vendor_team's policy      → subqueries vendor_company
vendor_team_member's policy → subqueries vendor_team + vendor_company
```

Written naively (each policy issuing a direct subquery against the other
tables), Postgres raises:

```
ERROR: infinite recursion detected in policy for relation "vendor_company"
```

Evaluating any one table's RLS policy re-triggers another table's policy
evaluation, which re-triggers the first — a genuine cycle, not a Postgres
bug. This is a predictable consequence any time two or more tables' RLS
policies are mutually referential (the "who can see this row" question for
table A depends on table B's rows, and vice versa) — a shape this codebase
will meet again as more relationship-holding entities are added (Vol 08
Identity OS, Vol 09 Relationship OS both describe multi-party access
patterns of this kind).

---

## Decision

When two or more tables' RLS policies need to reference each other, do not
let the policies query one another's tables directly. Instead:

```
1. Write ONE SECURITY DEFINER, STABLE, SET search_path = public function
   that computes the cross-table visibility set for the calling auth.uid()
   — e.g. "which company ids can this caller see, as owner or member."

2. The function's internal queries run as the function owner (this
   codebase's migration-running role), which BYPASSES RLS entirely on the
   tables it reads — the exact same mechanism every other SECURITY DEFINER
   write-RPC in this codebase already relies on for INSERT/UPDATE (S004-S005
   pattern), now applied to a read-time helper instead of a write.

3. Every table's RLS policy filters through this ONE helper — e.g.
   `USING (id IN (SELECT public._helper_name()))` — instead of querying
   the sibling tables directly. No policy ever triggers another table's
   policy evaluation, so there is no cycle.

4. REVOKE EXECUTE FROM PUBLIC, anon; GRANT TO authenticated — same grant
   discipline as every RPC (S005/S006 auto-grant trap). The helper must be
   regression-locked with a has_function_privilege test, same as any RPC
   (a helper with a silently-reinstated PUBLIC grant is a privilege bug,
   not just an RLS bug).

5. Name helpers with a leading underscore (`_vendor_company_ids_for_caller`)
   to mark them as internal plumbing, not a public API surface a client
   would call directly (PostgREST still exposes it if EXECUTE is granted —
   the REVOKE in step 4 is what actually closes that, the underscore is
   readability convention only, not enforcement).
```

### What this does NOT authorize

This pattern is for **row-visibility recursion** only — "can this caller
see this row at all," computed once per table via `IN (SELECT helper())`.
It is not a general license to compute row-dependent **column** masking
inside a policy or a view. S011 tried exactly that next (a
`security_invoker` view with a `CASE` expression to null `momo_number`/
`owner_person_id` for non-owner readers) and it does not work: Postgres
requires the invoking role to hold direct column privileges on every column
a `security_invoker` view references, even ones only reachable through a
masking `CASE` — so the "masked" columns would need to be granted to the
same role being masked from, which defeats the purpose, and that role could
then just query the base table directly and see the raw values. Column-level
masking (some readers see the whole row, others see a redacted version of
the *same visible row*) needs a `SECURITY DEFINER` **table-returning
function** instead — this codebase's own `discovery_feed()`
(20260630140004) already established that pattern for anon-safe curated
reads; S011's `get_vendor_company()` (20260702120005) is the vendor-domain
instance of it. Use the row-visibility helper (this ADR) for "can they see
it," and a curated read function (the `discovery_feed()`/
`get_vendor_company()` pattern) for "what do they see" when it differs by
caller.

## Reference example (S011)

```sql
-- 20260702120002_rls_vendor_company_team.sql
CREATE OR REPLACE FUNCTION public._vendor_company_ids_for_caller()
RETURNS SETOF UUID
LANGUAGE sql
SECURITY DEFINER
STABLE
SET search_path = public
AS $$
    SELECT vc.id
      FROM public.vendor_company vc
     WHERE vc.owner_person_id IN (
         SELECT id FROM public.person WHERE auth_user_id = auth.uid()
     )
    UNION
    SELECT vt.vendor_company_id
      FROM public.vendor_team vt
      JOIN public.vendor_team_member vtm ON vtm.vendor_team_id = vt.id
      JOIN public.person p ON p.id = vtm.person_id
     WHERE p.auth_user_id = auth.uid();
$$;

REVOKE EXECUTE ON FUNCTION public._vendor_company_ids_for_caller() FROM PUBLIC, anon;
GRANT  EXECUTE ON FUNCTION public._vendor_company_ids_for_caller() TO authenticated;

CREATE POLICY vendor_company_select_owner_or_member
    ON public.vendor_company FOR SELECT TO authenticated
    USING (id IN (SELECT public._vendor_company_ids_for_caller()));

CREATE POLICY vendor_team_select_owner_or_member
    ON public.vendor_team FOR SELECT TO authenticated
    USING (vendor_company_id IN (SELECT public._vendor_company_ids_for_caller()));
```

And for column masking, the separate function-based pattern
(`20260702120005_vendor_company_column_scoping.sql`):

```sql
CREATE OR REPLACE FUNCTION public.get_vendor_company(p_company_id UUID)
RETURNS TABLE (id UUID, name TEXT, momo_number TEXT, owner_person_id UUID, ...)
LANGUAGE plpgsql SECURITY DEFINER STABLE SET search_path = public
AS $$
    -- computes v_is_owner inline, then:
    -- CASE WHEN v_is_owner THEN vc.momo_number ELSE NULL END AS momo_number
$$;
```

## Consequences

**What this enables:** any future multi-party entity relationship (team
membership, organisation membership, shared-custody records — Vol 08/09
territory) can adopt this pattern immediately instead of rediscovering the
recursion error and reinventing a fix under time pressure.

**What this requires:** every new cross-referential RLS design must ask,
before writing the first policy, "will table A's policy need to read table
B, and B's policy need to read A?" If yes, write the helper first, not
after hitting the recursion error.

**What this does NOT affect:** single-table RLS policies with no
cross-table lookup (the majority of this codebase's existing policies —
`venue`, `person`, `gathering_tier`) are unaffected and need no change.

**Residual risk (accepted, not eliminated):** a `SECURITY DEFINER` helper
is, by construction, a privilege-bypass surface. It is scoped as narrowly
as possible (returns only an ID set derived from `auth.uid()`, takes no
caller-supplied filter arguments that could widen its result), but any
future edit to a helper's SQL body is a higher-stakes change than editing
an ordinary RLS policy, precisely because it bypasses the RLS the rest of
the schema relies on. Treat edits to any `_..._for_caller()` helper as
`zuka-security` review territory by default, not optional.

---

## Compliance Check (for future sessions)

Before writing RLS for a new entity, answer:

```
1. Does this table's policy need to read another RLS-enabled table to
   decide visibility? → check whether that other table's policy will, in
   turn, need to read THIS table. If yes, cyclic — write the helper first.
2. Does visibility differ from what's SHOWN (i.e. some readers should see
   fewer columns of a row they can otherwise see)? → that's the
   discovery_feed()/get_vendor_company() curated-function pattern, not
   this ADR's row-visibility helper. The two are complementary, not
   interchangeable.
3. New helper added? → REVOKE FROM PUBLIC, anon; GRANT TO authenticated;
   add a has_function_privilege regression test, same as any RPC.
```
