## Context

### What S007 actually built

The paid-ticket flow, end to end:

1. `initiate_ticket_purchase()` (SECURITY DEFINER RPC) creates a
   `PAYMENT_PENDING` `ticket` row with a **server-derived** `price_ugx` and a
   `tx_ref` stored in `ticket.attributes`
   (`supabase/migrations/20260630180001_fn_initiate_ticket_purchase.sql`).
2. `initiate-flutterwave-payment` (Edge Function — the only holder of
   `FLW_SECRET_KEY`) POSTs to `https://api.flutterwave.com/v3/payments`
   (`supabase/functions/initiate-flutterwave-payment/index.ts:120-135`) with:
   ```json
   { "tx_ref": "...", "amount": ticket.price_ugx, "currency": "UGX",
     "customer": {…}, "payment_options": "mobilemoneyuganda,card",
     "meta": { "ticket_id": "..." } }
   ```
   **There is no `subaccounts` key and no split configuration.**
3. Flutterwave returns a hosted checkout link; the buyer pays via MTN/Airtel MoMo.
4. `flutterwave-webhook` verifies the signature and calls
   `confirm_ticket_payment()`, which transitions the ticket to `ISSUED`.

### The exposure

Because the `/v3/payments` call carries no split, **all ticket revenue settles
into ZUKA's single Flutterwave account.** The money is the **organiser's** — a
ticket belongs to a `gathering`, and `gathering.organiser_id` is a third party
(`supabase/migrations/20260630130002_gathering.sql:28`, FK → `person`; at
marketplace scale, an S011 `vendor_company`). ZUKA collecting a third party's
sale proceeds and settling them onward later **is** the payment-aggregator /
money-transmission posture that:

- **CLAUDE.md forbids by constitution:** *"ZUKA is not a payment aggregator …
  vendor order money is vendor-direct"* (§5, and the Hard-Constraints block).
  The rule is written for vendor **orders**, but the legal shape of ticket sales
  is identical — ZUKA is the conduit for someone else's revenue.
- **Uganda's NPS Act 2020** regulates: holding/transmitting third-party funds
  without a licence is the exact activity the Act governs. (Legal conclusion for
  counsel — CLAUDE.md §8.)

**No live breach exists today** (no real ticket money has flowed), and **no
settlement schema exists** — there is no organiser payout account, no subaccount
record, no split-fee configuration anywhere in the migrations. This is a genuine
open decision, to be made **before** the first real paid ticket, not after.

### What ZUKA needs regardless of choice

Any compliant paid-ticket flow requires an **organiser-side settlement identity**
that Flutterwave can pay directly: the organiser's own MoMo/bank settlement
details and a Flutterwave **subaccount** created from them, plus the KYC that
onboarding implies. None of this is built (Vol 14 Ch 13 specifies it; S007 marked
it out of scope). That absence — not the code — is the true blocker.

## Decision (proposed)

**1 · Organiser ticket revenue settles organiser-direct. ZUKA never holds it.**
Paid ticket payments MUST route through **Flutterwave subaccounts (split
payments)**: the organiser's subaccount receives the ticket price and ZUKA
receives **only its platform fee**, taken as the split — the two legs settle
independently at Flutterwave, so organiser funds never rest in a ZUKA-controlled
balance. This is the same "vendor money is vendor-direct" posture CLAUDE.md
already mandates for vendor orders, applied to tickets.

**2 · MVP cut-line — paid ticketing is gated behind organiser subaccount
onboarding.** Until an organiser has a verified Flutterwave subaccount on file,
their gathering MAY NOT sell tickets that collect money into ZUKA's account.
Concretely:
   - **Free / RSVP tickets** (`price_ugx = 0`) need no settlement and ship
     unblocked — they carry zero aggregator exposure.
   - **Paid tickets** require the organiser's subaccount to exist; the
     `initiate-flutterwave-payment` call for a paid ticket MUST include the
     organiser's `subaccounts` split and MUST fail closed if it is absent.

**3 · ZUKA does NOT take the interim "collect-then-pay-out" shortcut** (Alt B
below) without explicit written Ugandan-counsel sign-off recorded in this ADR.
The wallet remains frozen; this ADR does not thaw it.

**4 · Settlement facts are events.** Every split/settlement outcome is recorded
as an append-only domain event (ADR-015) — `TicketRevenueSettled` (or equivalent,
name TBD in the build session) carrying `tx_ref`, organiser subaccount ref,
organiser leg, and ZUKA-fee leg — so reconciliation and DPPA/audit have a
truthful trail. No raw bank/MoMo PII in the event payload (by-reference;
[[CONCEPT_EventStore_PII_Erasure]] / candidate ADR-025).

**5 · BINDING INVARIANT — settlement MUST exclude `ticket_type='vendor'`.**
> ⚠️ **Any settlement/payout query, function, or view MUST filter out
> `ticket.ticket_type = 'vendor'` rows.** No organiser settlement, payout split,
> revenue reconciliation, or `TicketRevenueSettled` emission may ever include a
> vendor-credential ticket. This is not a style preference — it is a
> constitutional money-posture invariant, on the same footing as Decision §1.

**Rationale.** Vendor credential fees ride the **same `ticket` table** as
organiser ticket sales, carried as `ticket_type='vendor'` /
`provenance_origin='vendor_listing_fee'` (S019 —
`supabase/migrations/20260705110000_vendor_credential_presence.sql:45-50`, where
`'vendor'` was admitted into the `ticket_ticket_type_check` CHECK constraint).
But a vendor fee is **ZUKA's own B2B revenue**, not organiser ticket revenue —
it is Zuka charging a vendor for a listing credential, settled to Zuka directly.
Organiser settlement (Decision §1) pays the *organiser's* subaccount for tickets
*attendees* bought. If a settlement query swept up `ticket_type='vendor'` rows,
ZUKA would route its own vendor-fee income to a third-party organiser as if it
were that organiser's ticket sale — collecting and re-routing someone else's-
labelled money, which is exactly the payment-aggregator posture CLAUDE.md forbids
(*"vendor order money is vendor-direct"*, §5 + Hard-Constraints) and the NPS Act
2020 regulates.

**Origin.** S020 zuka-legal HARD finding
(`docs/sessions/archive/S020-2026-07-05-vendor-organiser-setup.md:406`), carried
via backlog item `settlement-exclude-vendor-tickets` and codified here:
> *"vendor credential fees are Zuka's B2B revenue, not organiser ticket revenue,
> despite sharing the ticket table — any future settlement/payout MUST exclude
> `ticket_type='vendor'` or Zuka is routing vendor money like an aggregator."*

**Enforcement (future, not built here).** This invariant is documented, not yet
executable — no settlement code exists to guard (Decision §2 gates it on counsel
sign-off + organiser subaccount onboarding). When real settlement logic lands, it
MUST ship with the backlog pgTAP guard `settlement-vendor-ticket-exclusion-test-pgtap`,
which turns this prose invariant into a hard-failing test: assert every
settlement path excludes `ticket_type='vendor'`. Until then, this ADR is the
binding gate — see the Compliance-check pre-build item below.

**Collection-side companion (do not miss when building the split).**

This §5 invariant governs **payout**. Its mirror at the **collection** step —
`initiate-flutterwave-payment` MUST POST a `ticket_type='vendor'` charge with
**no `subaccounts` key**, and the organiser subaccount split MUST exclude vendor
rows **in the same changeset that introduces the split, never after** — is
analysed in
[`ADR-026-COLLECTION-ADDENDUM-S065.md`](ADR-026-COLLECTION-ADDENDUM-S065.md)
(S065 `zuka-legal`, resolving S024 F-③). A session that builds the Decision §1
organiser split MUST read that addendum's §C/§D: shipping the split without the
collection-side vendor exclusion converts a correct non-aggregator flow into
aggregator routing at capture time.

> This is the **recommended** disposition. It keeps the constitution intact at
> the cost of deferring paid-ticket revenue until organiser onboarding (Vol 14
> Ch 13) is built. The founder may instead choose Alt B for a supervised pilot —
> but only on counsel's record.

## Alternatives considered

**Alt A — Subaccount split, organiser-direct (the recommended target above).**
Compliant end-state. Cost: requires organiser onboarding (settlement details +
Flutterwave subaccount creation + KYC), which is unbuilt — so paid ticketing
waits on Vol 14 Ch 13.

**Alt B — Interim: ZUKA collects into its account, pays organisers out manually.**
Fastest path to a paid transaction. **This is precisely the aggregator posture
CLAUDE.md forbids and the NPS Act regulates.** Only defensible, if at all, for a
tightly-scoped supervised pilot with (a) explicit written counsel sign-off, (b) a
hard cap on funds held and duration, and (c) a documented licence/exemption
basis. Default answer is **no**; recorded here so the temptation is named and
gated, not stumbled into.

**Alt C — MVP ships free/RSVP tickets only; all paid ticketing deferred until
Alt A is built.** The strictly-safe subset. Alt A's cut-line (Decision §2) already
achieves this incrementally — free tickets now, paid tickets as each organiser
onboards — without a hard "no paid tickets at all" freeze, so Alt A dominates C.

## Consequences

**Enables:** a paid-ticket flow that keeps ZUKA out of money-transmission — the
organiser is paid directly, ZUKA earns a transparent platform fee, and the
"not an aggregator" constitutional line holds under real money.

**Requires (build work, future sessions — not started here):**
- **Vol 14 Ch 13 organiser settlement onboarding**: capture organiser
  MoMo/bank settlement details (DPPA 2019 personal/financial data — `zuka-legal`
  + `zuka-security` gate), create the Flutterwave subaccount, store its reference
  against the organiser (`person` at MVP, `vendor_company` at marketplace scale).
- **`initiate-flutterwave-payment` change**: for a paid ticket, look up the
  gathering's organiser subaccount ref and add the `subaccounts` split to the
  `/v3/payments` body; **fail closed** (refuse to initiate) if it is missing.
- **Fee model**: where the ZUKA platform fee is defined (per-ticket / percentage),
  owned by `zuka-growth` (revenue_model) but constrained by this ADR.
- **`TicketRevenueSettled` event** registered in the Vol 14 Ch 15 event registry.
- Pairs with **R007-F2** (add the `tx_ref` index on `ticket`) since settlement
  reconciliation will query by `tx_ref`.
- **Vendor-ticket exclusion (Decision §5)** wired into every settlement path AND
  the `settlement-vendor-ticket-exclusion-test-pgtap` guard shipped alongside —
  no organiser settlement/payout code may land without both.

**Constrains:** the wallet stays frozen; no ZUKA-held balances; no
collect-and-payout without counsel sign-off (Decision §3).

**Does not affect:** the S007 rails as built for **free/RSVP** tickets, and the
buyer-side security work (JWT + ownership re-check, signed webhook, no-PII
logging) — all of which stand.

      licensable "payment service provider / aggregator" definition, given ZUKA
      never holds the organiser leg? (Counsel.)

      (Verify against Flutterwave docs before the build session asserts it.)
- [ ] **DPPA 2019** — organiser settlement details are personal/financial data:
      lawful basis, storage, RLS, and erasure posture defined before capture.
- [ ] **CLAUDE.md constitutional line** — the chosen option is consistent with
      "vendor money is vendor-direct" and the frozen wallet.
- [ ] **REQUIRED PRE-BUILD GATE — vendor-ticket exclusion (Decision §5).** No
      organiser settlement/payout implementation (Vol 14 Ch 13) may land until it
      **excludes `ticket_type='vendor'` rows from every settlement path** AND

      Vendor credential fees are ZUKA's B2B revenue, not organiser ticket revenue
