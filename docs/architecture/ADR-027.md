## Context

The compendium (Part II, gap #1) claimed ZUKA has no document stating "what is
NOT part of MVP." That claim is **false as stated** — `ZUKA_Appendix_J_
Dormant_Capability_Registry.md` already names ~40 dormant capabilities with
current DRL/CRL and graduation preconditions, and the Dormant Capability
Doctrine (Ch.14: *"architected does not mean activated… no capability may
activate solely because technology exists"*) already governs this
constitutionally, backed by ADR-016/017/008.

What's real is a narrower, different gap: **none of that doctrine is checked
mechanically.** Nothing today stops a future session — mine or another — from
creating a table or RPC that matches a named-dormant capability, or from
shipping a privileged function with no test, purely because no one happened
to notice during review. This is not hypothetical; it already happened twice
in this project's own history:

- **NOTICE-only tests** — `supabase/tests/` shipped tests that printed
  `[FAIL]` on a broken invariant but exited 0, so a real bug could not fail
  the suite. It took **seven sessions** (S010 through S017, per R005→R010
  findings in `docs/sessions/_INDEX.md`) to retire this pattern project-wide.
- **The PUBLIC-grant trap** — S004's write RPCs granted `EXECUTE` to
  `authenticated` but never issued the matching `REVOKE … FROM PUBLIC`,
  leaving them anon-callable. Caught at S005, not before.

Both were mechanically checkable — a grep would have caught either on the
commit that introduced it. Review caught them eventually, but "eventually"
cost real sessions. This ADR closes that class of gap going forward, without
re-authoring the kill-list that already exists.

## Decision

### 1 · A git pre-commit hook enforces three mechanically-checkable rules

Runs on any commit touching `supabase/`. No CI/CD infrastructure exists in
this repo today (verified: no `.github/workflows/`, no active git hooks) —
this is genuinely new tooling, chosen over a GitHub Actions workflow because
it fits the solo/local workflow with zero cloud infra and instant feedback.

```
(a) NOTICE-only test-sink check
    Fail if any file under supabase/tests/*.sql contains a '[FAIL]' marker
    (e.g. RAISE NOTICE '[FAIL]…') that is not followed, in the same
    exception/assertion block, by RAISE EXCEPTION. Closes the R005→R010
    debt class permanently — it cannot be reintroduced by an unnoticed copy-
    paste from an older test file.

(b) Untested-privileged-RPC check
    Fail if a new or modified migration defines a SECURITY DEFINER function
    whose name does not appear in at least one supabase/tests/*.sql file.
    Closes the class of bug the S004 PUBLIC-grant trap belonged to (a
    privileged RPC shipping without a test that would have caught it).

(c) Dormant-collision check
    Fail if a new or modified migration contains CREATE TABLE or CREATE
    FUNCTION for a name matching an entry in Appendix J's Dormant Capability
    Registry (e.g. any Historian/Twin/Opportunity-Engine/Memory-Engine name),
    unless the migration file's header comment cites the ADR/Activation
    Contract that graduates it (mirrors the existing "-- see ADR-021"
    citation convention already used in this codebase).
```

Checks (a)–(c) are implemented **once**, as a shared script (e.g.
`scripts/check-migrations.sh`), not duplicated between the hook and CI below
— two copies of the same three greps would drift.

### 1b · A GitHub Actions workflow backstops the same three rules, plus the full test suite

A pre-commit hook only runs on the founder's own machine and is bypassable
(`--no-verify`, or simply not installed after a fresh clone). This repo
already has a real remote (`Kiyingijmc/zUKa`), so a second, non-bypassable
layer is justified — defense-in-depth, the same "cheap filter + real
authority" shape ADR-023 already uses for the offline scanner (Bloom
pre-filter, exact hash the real authority).

```
Trigger: on every push (this project commits straight to main; no PR-based
         workflow exists, so branch-restricting to `main` alone would miss
         the actual commit pattern — trigger on push, any branch).
Steps:   1. checkout
         2. install the Supabase CLI (GitHub-hosted Ubuntu runner — no WSL2
            layer, so the local supabase-status health-check flakiness
            CLAUDE.md's "Watch out" section documents does not apply here;
            this doubles as an independent, quirk-free confirmation that
            migrations apply cleanly)
         3. `supabase start` (no --ignore-health-check needed on this runner)
         4. `supabase db reset` — applies every migration from clean
         5. run every file in supabase/tests/*.sql via psql; fail the job on
            any non-zero exit (this is what actually catches a RAISE
            EXCEPTION a NOTICE-only test would have swallowed)
         6. run scripts/check-migrations.sh (the same (a)-(c) checks as the
            pre-commit hook) against the diff since the previous push
```

This is not a replacement for the pre-commit hook (instant local feedback
still matters for a solo workflow) — it is the backstop for when the hook
didn't run, was bypassed, or the local WSL2/Docker environment gave a false
signal.

### 2 · Session-level ritual, extending the S019 front-matter/preflight pattern

For judgment calls a grep cannot make (`(c)` catches an exact name match, not
"this is dormant-*adjacent*"):

```
- Session front-matter gains: touches_dormant_capability: none | <registry-name>
- If non-`none`: the session's preflight must assert the capability's current
  state before work starts — the same pattern S019 §1 already uses
  ("# expect: does not exist").
- If non-`none`: zuka-reality-checker becomes a MANDATORY gate for that
  session (not optional, not founder-waivable by omission).
- Single waiver path: only an explicit founder message, or a completed
  Appendix J graduation (its existing six-step procedure), may cross the
  boundary. No session self-authorises.
```

### 3 · A standing 3-question checklist for future architecture proposals

Added to `docs/sessions/_TEMPLATE.md` as a pre-proposal check — this is what
replaces a full multi-agent audit for the *next* "should we build X" moment:

```
1. DRL/CRL floor — does manifestation_depth ≤ min(DRL_permits, CRL_earned)
   already hold for this capability? No → stop; it is dormant, not a
   candidate, regardless of engineering merit.
2. Rule-of-Three + zero-cost seam — do 3 concrete real instances of the need
   already exist? No → reserve a zero-cost seam only (a column, an enum
   value, a naming convention) and stop there. Yes → build-eligible.
3. Opportunity-cost — is this a better use of THIS session than the current
   critical path? No → backlog it. Yes → build now.
```

### 4 · Appendix J gains concrete activation triggers for its 4 named dormant engines

Not new dormant entries — these four already exist in the Registry. This adds
the *trigger* each currently lacks, converged independently by two agents in
the 2026-07-05 brainstorm (`BRAINSTORM_2026-07-05_Findings.md` §3):

```
Opportunity Engine   → ≥50 repeat organisers (≥3 gatherings each) AND high
                        VendorPresenceActivated volume (a real two-sided pool)
Digital Twin Engine  → multiple concurrent scanner_sessions per gathering
                        (multi-gate) AND organisers requesting live capacity
                        visibility mid-event
Memory Engine        → median attendee has ≥3 check-ins over ≥6-12 months
                        (a real corpus; AttendanceSeedRecord is already being
                        seeded — only the surface stays dormant)
Intelligence Engine  → feed impression→click logging exists AND DRL reaches
                        2+ (recommending on DRL-1 data is forbidden regardless)
```

## Alternatives considered

**Alt A — Fully automated (GitHub Actions CI) as a *replacement* for local
enforcement.** Rejected in that form: instant local feedback still matters
more than a remote-only gate for a solo workflow, and a PR-based review
ceremony doesn't fit how this project commits (straight to `main`). **Adopted
instead as a complementary backstop** (Decision §1b) — pre-commit for speed,
CI for defense-in-depth against a bypassed/missing hook and against local
WSL2/Docker-Desktop environment quirks (CLAUDE.md's "Watch out" section).
The repo already has a real GitHub remote, so the infrastructure cost is
just the workflow file, not a new hosting decision.

**Alt B — Pure ritual, no automation.** Rejected: ritual alone already failed
to catch the NOTICE-only debt for seven sessions and the PUBLIC-grant trap
for one. A grep-checkable rule left to review discipline alone has already
proven it can slip.

**Alt C — A hard technical lock (reserve nothing until ADR time; dormant
seams don't exist even as empty schema).** Considered and rejected as too
rigid — it conflicts with a pattern this project already uses productively
(the nullable `embedding vector(1536)` column, the feed system's reserved
provenance axis). Reserving a zero-cost seam ahead of time is explicitly
allowed by the Decision §3 checklist; this ADR enforces the *build*
boundary, not the *seam* boundary.

## Consequences

**Enables:** the two debt classes that already cost this project real session
time (NOTICE-only tests, untested privileged RPCs) become structurally hard
to reintroduce — "cannot commit, and cannot land even if it was" instead of
"caught by a diligent reviewer." Future "should we build this engine"
questions get a 3-question checklist instead of a full audit. As a side
effect, CI running on a clean Ubuntu runner gives an independent, quirk-free
confirmation that migrations apply and the full suite passes — useful given
the local WSL2/Docker-Desktop health-check flakiness already on record.

**Requires (build work, not started here):**
- A shared script implementing checks (a)–(c) once, called by both the
  pre-commit hook and the CI workflow (no duplicated/drifting logic).
- The pre-commit hook itself, wired to call that shared script.
- A GitHub Actions workflow (`.github/workflows/`) that provisions Supabase,
  resets the DB, runs the full `supabase/tests/*.sql` suite, and calls the
  same shared script — tested against one deliberately-broken case and one
  clean case per rule, same as the hook.
- `docs/sessions/_TEMPLATE.md` updated with the front-matter field and the
  3-question checklist.
- `ZUKA_Appendix_J_Dormant_Capability_Registry.md` updated with the four
  activation triggers in Decision §4.

**Constrains:** no session may create a name colliding with the Dormant
Registry without citing the graduating ADR; no privileged RPC may ship
without a matching test; no test file may ship with a NOTICE-only fail sink.

**Does not affect:** code already shipped (S001–S019). This is enforcement
for new work going forward, not a retroactive re-litigation — existing
NOTICE-only tests are already tracked separately for backfill (R010-F1,
`docs/sessions/_INDEX.md`).

**Explicitly out of scope for this ADR** (real, but separate doc-hygiene
items from the same brainstorm, not architecture decisions): the stale
`ZUKA_ADR_Catalog.md` (missing ADR-021/022/023/026 rows) and the bible-v4
two-axis vs. downstream three-axis (DRL×CRL vs DRL×BRL×CRL) inconsistency.
Both are flagged in `BRAINSTORM_2026-07-05_Findings.md` §5.2 as their own
small fixes.
