# ADR-021 — Caching Strategy: Discovery Feed vs Transactional Paths

> **Status:** PROPOSED (pre-production; local dev is unaffected)
> **Date:** 2026-06-30
> **Authority:** Architecture Council · Adaptive Zone (requires founder sign-off
> before production deployment)
> **Relates to:** Vol 15 (Discovery), Vol 20 (Infrastructure & Connectors),
> the locked stack (Cloudflare is constitutional), ADR-015 (append-only events)
> **Discovered:** Post-S006 architectural review, June 2026

---

## Context

Six development sessions have produced a working backend: discovery, ticketing,
check-in, identity, and entry. Before any Flutter client or production deployment
consumes these RPCs, the caching posture must be an explicit, written decision —
not an assumption.

Three facts drive this decision:

1. `discovery_feed()` is the highest-volume RPC in the MVP. Every anonymous
   visitor calls it on app open. It returns relatively stable data (a gathering
   doesn't change state every second). Hitting Postgres directly on every call
   will not scale and will expose the database to unnecessary load.

2. `check_in_ticket()` processes physical venue entry against a rotating QR
   token. Any caching of this response — at any layer — is a ticket-cloning
   vulnerability. The rotating `qr_token` column only provides fraud protection
   if every scan reads live database state.

3. These two requirements are in direct tension: the instinct to add a caching
   layer for performance must be stopped at the door of the transactional paths.
   Without a written rule, a future engineer (or a future session) will
   inadvertently cache a check-in response. That rule must be this ADR.

---

## Decision

### Rule 1 — Discovery feed: cached at the Cloudflare edge (production only)

```
SCOPE:      discovery_feed() RPC only
LAYER:      Cloudflare Cache Rules (already in the locked stack, Vol 20)
TTL:        30 seconds (balances "live now" freshness with load reduction)
INVALIDATION: cache-key includes the request's geo-zone (PostGIS feed is
              location-aware); Supabase Realtime triggers an invalidation
              webhook when a Gathering transitions to LIVE or ENDED
LOCAL DEV:  NO CACHE — hit Postgres directly; no Cloudflare config in dev
PRODUCTION: REQUIRED before any marketing launch or public traffic
```

Rationale: 30-second staleness is acceptable for discovery. A gathering going
live appearing 30 seconds late in someone's feed is a tolerable trade-off for
protecting Postgres from discovery-query storms at event launch time. A Realtime
invalidation webhook on LIVE/ENDED transitions reduces worst-case staleness to
the webhook propagation latency (~1-2 seconds) for the most critical transitions.

### Rule 2 — Check-in path: NEVER cached, at any layer, ever

```
SCOPE:      check_in_ticket() and any future admission-verification RPC
LAYER:      All layers — Cloudflare, CDN, application, client
RULE:       Zero TTL. No cache headers permitting storage. Cache-Control:
            no-store on the PostgREST response.
ENFORCEMENT: Every future migration or Edge Function touching the check-in
             path must include a comment: "NO-CACHE: see ADR-021"
```

Rationale: the rotating `qr_token` column (generated on ticket creation,
invalidated on check-in) is the fraud-prevention mechanism. It functions only
if the scanner reads live DB state on every scan. A cached "PASS" response
allows a photographed QR to admit two people. This is not a performance
trade-off; it is a security invariant with the same status as the
trust-state non-exposure rule.

**Override rule:** no future ADR may introduce caching on any admission or
ticket-validation path without an explicit security review from `zuka-security`
and founder sign-off. The bar for overriding this rule is the same as overriding
a Stable-Zone constitutional decision.

### Rule 3 — All other paths: no caching by default

```
Authenticated RPCs (create_gathering, publish_gathering, go_live,
issue_ticket, create_scanner_session): no cache. These are transactional
and must reflect live state.

Payment webhook endpoint (S007+): no cache. Verified once, acted on once.

person / ticket / venue / domain_events direct reads: not applicable —
direct client reads are blocked by RLS + REVOKE; clients use RPCs only.
```

## Consequences

**What this enables:** a production discovery experience that doesn't hammer
Postgres on every app open; a check-in path that is structurally safe from
cache-based ticket cloning; a clear written boundary that future sessions can
cite rather than rediscover.

**What this requires (production only):**
- Cloudflare Cache Rules configuration for the discovery endpoint
- A Supabase Realtime webhook → Cloudflare Cache Purge integration
  (or a periodic 30-second TTL accepted as sufficient)
- `Cache-Control: no-store` on the PostgREST route for check_in_ticket

**What this does NOT affect:**
- Local development — no Cloudflare config, no caching, Postgres direct
- The Flutter client's local state management (a separate design concern,
  see CONCEPT_Unspecced_Features_Register.md §6 "Application-Layer Caching")
- pg_cron scheduled jobs (a different domain — see the same register §6)

---

## Compliance Check (for future sessions)

Before introducing any new caching layer or CDN rule, answer:

```
1. Does this RPC verify, issue, or admit? → NO CACHE (Rule 2)
2. Does this RPC handle money? → NO CACHE (Rule 3)
3. Is this discovery_feed() or a read-only, anonymous, non-transactional RPC?
   → CACHE IS PERMITTED under Rule 1, with the documented TTL and
     invalidation trigger.
4. Everything else → NO CACHE by default; propose a new ADR if needed.
```
